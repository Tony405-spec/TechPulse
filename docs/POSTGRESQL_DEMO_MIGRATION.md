# PostgreSQL development and synthetic demonstration data

This guide documents the isolated local development setup used to test the TechPulse demo migration. It does not replace the original research database.

## Database separation

- Existing `TechPulse-Database` and `techpulse_db` were not changed.
- Development target: `techpulse_rebuild_dev` on localhost port 5432.
- Canonical research schemas remain `raw`, `staging`, `core`, `analytics`, `ml`, and `audit`.
- Synthetic fictional data is separated in PostgreSQL schema `demo` and retains the `data_mode` and `data_origin` fields from the inspected source.
- The original SQLite fixture remains an immutable migration source/backup. Streamlit reads the PostgreSQL `demo` schema only.
- A checksum in `demo.migration_manifest` identifies the imported source. An identical rerun verifies record counts. A different checksum fails without replacing existing records.
- Synthetic model-selection decision and criteria are recorded in `demo.model_selection_records` by migration 005; the visible model comparison is calculated from the persisted evaluation metrics.

## One-time migration

Create a local `.env` using `.env.example` and set `DATABASE_URL` to the new development database with a restricted read role. Do not place the PostgreSQL administrator password in a tracked file.

As the database owner, apply numbered migrations:

```powershell
$env:DATABASE_URL = "postgresql+psycopg2://postgres@localhost:5432/techpulse_rebuild_dev"
python -m techpulse.cli db-migrate
```

If this is a fresh database, demo-dependent migrations are intentionally deferred until the source tables exist. Run the read-only source import below, then run `python -m techpulse.cli db-migrate` again to apply the demo view and model-selection migrations.

Use an interactive password prompt or local PostgreSQL passfile for the administrator credential. Then run the source migration with the same target URL:

```powershell
python -m dashboard.postgres_demo_migration --source outputs/synthetic_demo/techpulse_demo.sqlite
python -m techpulse.cli db-migrate
```

The source is opened read-only and checked with `PRAGMA integrity_check`; its SHA-256 and exact table counts are recorded. This tool must not be used as an application data source. The checked source checksum is `f035a6a9baa246b4e42e2663e5c7f58de8de419233a2db7c37f0cd0c944b3caf`.

## Verification

The migrated source contained 25 tables and 210 technologies, 15,120 community observations, 8,400 discussion rows, 3,360 survey-like rows, 300 fictional companies, 1,500 relationships, 2,000 fictional adoption scenarios, 1,260 generated geography rows, 8,820 feature snapshots, four synthetic model runs, 840 predictions, and 1,470 explanation records. Kenya-labelled generated geography rows are fictional and not Kenya research observations.

The selected demonstration best model is calculated from PostgreSQL `demo.model_metrics` and `demo.model_runs` by macro F1 and shown only as a synthetic demonstration result. It is not a research winner. Research mode has zero successful canonical model runs in this development database.

The provided local restricted role is `techpulse_rebuild_app`, with SELECT-only access in the development database. Do not use the postgres administrator role to run Streamlit.

When setting up a different database/role, grant that restricted role `CONNECT`, `USAGE` on the needed schemas, and `SELECT` on the demo tables/views after migrations. Do not run the dashboard as the schema owner.

For this local checkout, `.env` already points at the restricted development role and database. Keep its credential value in the git-ignored file, not a shell command or tracked document. Start the application:

```powershell
python -m streamlit run dashboard/app.py
```

In pgAdmin, register the local PostgreSQL server and open `techpulse_rebuild_dev`. The `demo` schema is intentionally separate from research schemas. For counts and constraints, run:

```sql
SELECT count(*) FROM demo.technologies;
SELECT count(*) FROM demo.predictions;
SELECT n.nspname AS schema_name, r.relname AS table_name, c.conname, c.contype
FROM pg_constraint c JOIN pg_class r ON r.oid=c.conrelid
JOIN pg_namespace n ON n.oid=r.relnamespace
WHERE n.nspname='demo' ORDER BY r.relname, c.conname;
SELECT source_sha256, migrated_at, row_counts FROM demo.migration_manifest;
SELECT selection_key, model_run_id, primary_metric, primary_score, selection_status, criteria
FROM demo.model_selection_records;
```

## Important limitation

The source database includes artifacts generated by a separate demo training script. Those artifacts, labels, model metrics, company identities, adoption records and Kenya-labelled examples are fictional demonstration material. They do not constitute empirical validation, verified enterprise adoption, or Kenya-specific evidence. No valid research model is registered by importing these records.
